02建图：从零采一张图

换新场地的第一件事。两种方式：方式 A——SDK 建图会话（推荐），四个 API 端点全程搞定；方式 B——课程手动流程（下方六步，作为底层参考与兜底）。产物都是四件套：map.pcd（FAST-LIO 重定位参考云）、ground_map.pcd、mymap.pgm + mymap.yaml（2D 栅格）。

方式 A：SDK 建图会话（仿真已端到端验证）

# 1. 开始录制：自动停导航栈、起 FAST-LIO 建图栈（约 2s）
curl -X POST :1448/api/core/slam/v1/mapping/:start
# 2. 驱动机器人慢走全场：真机用遥控器；或用 MoveAction 速度遥控
#    （建图中导航/导览被 mapping_running 互锁拒绝，遥控保持可用）
curl :1448/api/core/slam/v1/mapping          # 随时看会话状态
# 3. 结束并入库：存 2D 栅格 → 停栈触发 pcd 保存（校验新鲜度）→ 打包注册
curl -X POST :1448/api/core/slam/v1/mapping/:finish \
     -H 'Content-Type: application/json' -d '{"map_id":"showroom-1f","name":"一楼展厅"}'
# 4. 立即可用：:select → :relocalize → 导航（放弃录制用 /mapping/:cancel）

会话结束后建图相关 ROS 进程全部自动停止，任意时刻只有一套 SLAM 栈在跑。真机前置配置：G1_API_MODE_MAPPING_LAUNCH_FILE=…/g1_api/deploy/g1_api_mapping.launch。/sdk 网页「建图录制」分组可以点着走完全程。

所有 ALLOW_* 默认 false。每层只开当层需要的开关（G1_API_SAFETY_<FLAG>=true，改完重启服务），确认无误再进下一层，别跳层。

1mock·PC2无/healthz、/robot/info 能通（验证环境装对）无
2real·PC2全关只读端点 + /robot/health 互锁清单符合预期无
3real·PC2VOICE + ARMarm action-list 权威表、说一句 TTS低

红线

ALLOW_MOTION（MoveAction 速度遥控，不避障）只在有人持急停在场时打开；急停类停止命令永远放行，不受任何开关限制。

06已知陷阱（都实测踩过或源码考证过）

  • 课程 README 大面积过时：真实栈是 ROS1 Noetic，所有 ROS2/rclpy 字样都是残留，禁止 import rclpy。
  • 网卡默认值三处不一致（eth0 / eno1 / enp4s0）——g1_api 强制显式配置，不设就拒绝启动。
  • 切图 launch 的 2D 图参数叫 grid_yaml 不叫 2dmap_file：ROS 名不能以数字开头，命令行上 2dmap_file:=… 会被当成话题重映射静默失效。
  • move_base 在重定位前会阻塞等 map TF——/move_base/status 话题出现是"已重定位"的信号，不能拿来当启动就绪判据（g1_api 内部已按此实现）。
  • TTS 前必须先 LocoClient.Init()，否则静默失败；中文 JSON 需 ensure_ascii=False。
  • 到点判定用 TF 距离，不依赖 /move_base/result。
  • 手臂 action_id 31 不在 SDK 表内——真机先 GET /arm/v1/action-list（内部调 GetActionList）拿权威表。
  • G1 旋转机构物理限位约 ±1.3 rad，导览点朝向容差建议 ≥0.5 rad。
  • 建图后 yaml 的 nan 改 0.0（yaml-cpp 连 -0 整数都会拒绝）。
  • 如果 g1_api 异常退出，它拉起的导航 roslaunch 可能变成孤儿进程——新实例 :select 时会自动清理同名 launch（已内置）。

DDS 并行须知

g1_control_vel.py 不会独占 eth0——DDS 是多参与者总线，任意多个进程可同时在同一网卡上初始化并与机器人通讯（课程的 agent_server 与速度桥本就长期共存）。机器人本体的 loco（运动）/ voice（TTS/音量/LED）/ arm（手臂）是相互独立的 RPC 服务，灵巧手走 TCP 更与 DDS 无关：调灯光、手臂动作可随时与导航并行（导览"到点后动作+语音同时执行"依赖的就是这种并行）。

唯一要防的是运动指令双源冲突（语义层，不报错）：move_base 经 /cmd_vel 发速度的同时又有人直接调 LocoClient.Move()，机器人执行最后到达者，表现为抽搐抢方向。g1_api 的单槽位动作模型已把这挡住——只要不绕过 API 手动同开两个运动源就不会遇到。手臂动作建议站定时执行（行走中执行由本体仲裁，行为无文档保证）。

09可选 planner：AeroMaze（源码编译）

自研 planner 栈 AeroMazePlanner-ST-nav（navigation 全家桶 fork + 自定义 PathBoundryLayer 走廊约束插件 + G1 专调参数）。以 overlay 工作区形式并存：aero 已是默认 planner；一个环境变量切回课程栈，随时可回退。

与课程栈的三点不同

① move_base/costmap_2d/TEB 全部源码编译（apt 版没有 PathBoundryLayer 插件）。② TEB 终点容差 xy 0.25 m / yaw 0.25 rad（试验值，改 robot_settings/cfg/G1/teb_local_planner_params.yaml），move_base 自己就能把位置和朝向都收住。③ 因此 g1_api 的到点判定切到 planner 反馈模式：直接消费 /move_base/result（SUCCEEDED=到点 / ABORTED=失败并带原因），TF 只做事后校验，三阶段细调只在校验不过时兜底。课程模式的"TEB xy 容差 ≤ reach_threshold"不变量在此模式下不适用。
